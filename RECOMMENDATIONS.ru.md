# land-it: аудит проекта и рекомендации по развитию

Дата: **24 октября 2026 года**. Проверенная версия: **0.6.0**, коммит `6d07c8389dcd52339e34324d45b013b01c533007`.

Документ подготовлен по запросу на изучение текущего проекта и возможной версии для ChatGPT. Это рекомендации к следующему этапу разработки. Со стороны аудита добавлен только этот файл; настройки пользователя и GitHub не изменялись. При финальной проверке обнаружены параллельные изменения CLI и тестов; они не перезаписывались. Основные выводы и номера строк относятся к коммиту выше; наблюдаемые новые правки отдельно учтены в разделе 17.

## 1. Главный вывод

**Проект стоит развивать. Сначала нужно укрепить достоверность проверок и ревью, затем выделить общее ядро и подключить Claude Code, Codex и ChatGPT через отдельные адаптеры.** Копирование текущего плагина с заменой названий перенесёт в новую версию существующие ошибки и ограничения.

Ценность land-it — организация инженерного процесса вокруг ревью: проверки, оценка риска, ответы на замечания, история, допуск к PR и обучение на инцидентах. Это более устойчивое позиционирование, чем обещание конкретной модели «делать хороший code review».

Сейчас это работоспособный прототип с полезными функциями и тестами, но некоторые заявления в README сильнее фактических гарантий. Штамп доказывает совпадение дерева с локальным состоянием `green`; он пока не доказывает завершение ревью, актуальность анализа PR на GitHub или соответствие политики целевой ветке.

Для версии OpenAI предлагаю два варианта поставки из одного проекта:

1. **Локальная версия для Codex / подходящих сред ChatGPT Work**: CLI, skills, адаптер lifecycle hooks, доступ к рабочему репозиторию. Это ближайший аналог текущего продукта.
2. **Версия для ChatGPT через MCP**: работа с PR, результатами CI, замечаниями и отчётами через контролируемый сервис. Проверки кода выполняет отдельный runner. Это удобный интерфейс к тому же процессу для пользователей без локального coding agent.

Обычная инструкция или загружаемый файл в чате может помочь с ревью, но сам по себе не создаёт технический допуск к merge. Место исполнения кода, полномочия инструментов и правила GitHub нужно проектировать явно.

## 3. Что уже сделано хорошо

- **Небольшое ядро без внешних Python-зависимостей.** Проще устанавливать и проверять. Сам размер `bin/land-it` — 1 071 строка — пока управляем, хотя дальнейшее расширение уже требует модулей.
- **Разделение механики и суждения.** Python отвечает за Git, checks, состояние и hooks; skills — за интерпретацию изменений. Это хорошая основа многоплатформенной архитектуры.
- **Привязка к дереву Git.** Лучше флага «ревью было»: реальные изменения можно обнаруживать независимо от текста ответа модели. Учтён неприятный случай same-size edits и времени индекса.
- **Изолированный индекс для снимка.** Реальный staging пользователя не заменяется обычным `git add -A`.
- **Доверие к командам конфига.** Изменение `checks` и `on_edit` требует повторного разрешения. Модель угроз уже учитывает выполнение команд через hooks.
- **Разумная экономия.** Checks перед дорогим ревью, ограничение раундов, review effort по риску, path-scoped checks, отсутствие `max` по умолчанию.
- **Журнал находок и разбор обратной связи.** Есть начало замкнутого процесса от замечания к исправлению и eval.
- **Тесты на временных репозиториях.** Проверяется реальное поведение Git и CLI, а не только изолированные функции.
- **Русская и английская документация, changelog, MIT.** Проект уже оформлен для распространения.

Эти решения следует сохранить при рефакторинге. Переписывать рабочую Git-механику на другой язык только ради адаптера ChatGPT не требуется.

## 4. Приоритетные дефекты и разрывы гарантий

Приоритеты: **P1** — исправить до широкого распространения и переноса автоматических допусков; **P2** — следующий этап надёжности и удобства; **P3** — расширение после стабилизации. Здесь P1 не означает, что обнаружена эксплуатация в реальном проекте: речь о воспроизводимой ошибке или существенном нарушении заявленного поведения.

### R01 · P1 · Начатый раунд ошибочно считается завершённым ревью

**Где:** `bin/land-it:284`, `bin/land-it:305`, `skills/preflight/SKILL.md:26`.

`round` записывает снимок до checks и ревью. Повторный вызов на том же дереве возвращает `already_reviewed: true`. Skill по этому признаку предлагает пропустить шаги 4–7. Если первый запуск остановился после создания раунда — из-за красной проверки, отмены или недоступного reviewer — ревью могло вообще не состояться.

**Подтверждено:** два последовательных `round` без единого запуска reviewer дают `already_reviewed: true`.

**Изменение:** состояния `started`, `checks_passed`, `review_completed`, `resolved`, `stamped`; завершение ревью — отдельная запись с деревом, диапазоном, версией правил и результатом. Повторять можно только действительно завершённые шаги. Исправить также номера шагов в skill: ссылка на 4–7 сейчас захватывает findings, stamp и PR body.

**Приёмка:** прерванный preflight возобновляется с незавершённого шага; повторный старт не создаёт доказательства ревью.

### R02 · P1 · Штамп не требует результата ревью

**Где:** `bin/land-it:403`.

Для `stamp` достаточно `green == tree`, допустимого tier и отсутствия открытых findings. Нет проверки существования завершённого раунда, запуска code/security review, выполнения behavior check, лимита раундов или результата последнего reviewer. `check → stamp` может пройти без ревью; пустой ledger трактуется как отсутствие проблем.

**Изменение:** ввести обязательные результаты этапов по risk policy. `skipped` допустим только с разрешённой причиной. Политику проверяет ядро; skill помогает пройти этапы. Сохранить ручной override как явную аудируемую операцию с причиной и полномочиями, если он нужен продукту.

Локальная запись, доступная тому же пользователю и агенту, не является криптографическим доказательством независимого ревью. Для командной гарантии окончательный статус должен формироваться доверенным CI/сервисом.

### R03 · P1 · Неудачная повторная проверка сохраняет прежний зелёный статус

**Где:** `bin/land-it:389`, `bin/land-it:415`.

Успешный `check` записывает `green`, а неудачный не инвалидирует прежнюю запись и штамп. Один и тот же tree может стать красным из-за окружения, внешнего сервиса или нестабильного теста, но продолжить считаться проверенным.

**Подтверждено:** успешная проверка, затем неуспешная на том же дереве, затем `stamp` — последняя команда завершается с exit 0.

**Изменение:** хранить check run с результатом и контекстом; новый запуск переводит актуальную проверку в `running`, ошибка — в `failed`. Штамп должен ссылаться на успешный актуальный run, а не просто на когда-либо зелёное дерево.

### R04 · P1 · Команды проверок могут изменить дерево, которое затем объявляется проверенным

**Где:** `bin/land-it:366`, `bin/land-it:393`.

`cmd_check` вычисляет tree после исполнения команд. Если поздняя команда изменяет файл, ранняя проверка фактически проверяла старое содержимое, а зелёным становится новое. Возможен и конкурентный edit во время длительной проверки.

**Подтверждено:** первая проверка успешно проверяет содержимое файла; вторая заменяет его на некорректное; `check` и `stamp` завершаются успешно, независимое повторение первой проверки уже падает.

**Изменение:** разделить mutating preparation — format/fix/codegen — и проверку. Сравнивать дерево до и после checks. При изменении выдавать `tree_changed_during_checks` и требовать повторения. Для длительных или параллельных запусков проверять неизменяемый snapshot в отдельном worktree/runner.

### R05 · P1 · Штамп связан с локальным деревом, но не со всем контекстом изменения

**Где:** `bin/land-it:418`, `bin/land-it:957`.

В штампе только `tree`, `tier`, `at`. PreToolUse сравнивает его с локальным `HEAD^{tree}`. Не сохраняются repository identity, target branch/base SHA, фактический PR head SHA, версия политики и правила ревью. Одно дерево при разных базах может давать разный diff и риск. Локальный HEAD также не доказывает, что GitHub PR уже обновлён до него.

**Изменение:** разделить локальный preflight receipt для дерева и серверный PR receipt для конкретных `repo + PR + head_sha + base_sha`. При push, retarget, rebase и обновлении обязательной политики пересчитывать применимость. Перед merge проверять актуальные GitHub checks и approvals на текущем PR head; использовать поддерживаемую проверку ожидаемого SHA на стороне интеграции.

**Приёмка:** нельзя применять receipt к другому контексту repo/base/head без проверки применимости. Повторное использование результата допустимо, если доказано совпадение всех значимых входов и требуемый тип проверки допускает его.

### R06 · P1 · Regex-перехват `gh` не является полным контролем PR-операций

**Где:** `bin/land-it:945`, `bin/land-it:957`, `hooks/hooks.json:34`.

Правила узнают конкретные текстовые формы `gh pr create/merge/review`. Альтернативное расположение global flags, shell wrapper, API-вызов, другой инструмент или смена каталога внутри shell не описаны надёжным структурным контрактом. В частности, `gh -R OWNER/REPO pr ...` не соответствует текущим regex.

**Подтверждено:** проверены решения hook для `gh --repo owner/repo pr create`, создания PR с другим `--head` и перехода в другой каталог внутри команды. Реальные PR не создавались и не сливались; валидность позиции global flag проверена локальным `gh ... --help`.

**Изменение:** локальные hooks позиционировать как вспомогательную защиту от ошибок. Ввести явные операции `land-it pr prepare/create/merge` с разрешением реального repo/head/base, а окончательное соблюдение правил закрепить в GitHub. Не пытаться обещать полную безопасность, расширяя regex до самодельного shell parser.

Обещание «агент никогда не утверждает PR» относится лишь к охваченным вызовам. Человеческое одобрение нужно отличать по идентичности и процессу авторизации, а не по совпадению команды с регулярным выражением.

### R07 · P1 · При неизвестной базе риск может стать `low` для уже закоммиченного кода

**Где:** `bin/land-it:221`, `bin/land-it:264`.

Если merge base не найден, используется сравнение с `HEAD`. Уже закоммиченные изменения текущей ветки исчезают из списка. Пустой список классифицируется как `low`. Возможные условия: основная ветка называется иначе, база не настроена, shallow history или неверный ref.

**Подтверждено:** после переименования основной ветки в `trunk` feature-ветка с закоммиченным файлом в `src/auth/` получила `tier: low`, `files: {}`.

**Изменение:** отсутствие достоверной базы — отдельная ошибка `base_unavailable`, блокирующая stamp. При подключённом PR получать его base; в локальном режиме позволять явный `--base`. Не путать «diff пуст» и «diff не удалось вычислить».

### R08 · P1 · Переименование и Unicode-пути могут занизить риск

**Где:** `bin/land-it:264`, `bin/land-it:814`, аналогичные разборы вывода Git.

`git diff --name-only` разбирается по строкам. При rename учитывается новый путь, а удаление из чувствительной области может потеряться. Git также способен выдавать quoted/escaped имена, не совпадающие с glob.

**Подтверждено:** rename `src/auth/access.py → docs/access.md` дал `low`; файл `src/auth/пароль.py` под high glob получил `medium` из-за представления имени Git.

**Изменение:** получать `--name-status -z`, корректно разбирать rename/copy и учитывать старый и новый путь. Для списков файлов использовать NUL-delimited вывод. Добавить имена с Unicode, пробелом, табуляцией и переводом строки в тесты; отдельно deletion, type change и symlink.

### R09 · P1 · `git blame` не доказывает, что дефект существовал до PR

**Где:** `bin/land-it:309`, `bin/land-it:337`, `skills/preflight/SKILL.md:67`.

Старая строка может стать ошибочной из-за изменения вызывающего кода, конфигурации, схемы данных или проверок рядом. Сейчас возраст строки автоматически переводит finding в `pre-existing`, а открытой проблемой он уже не считается.

**Подтверждено:** в базе `divide(x)` содержит `return 10/x`; PR добавляет вызов `divide(0)`. Finding на строке деления автоматически получает `pre-existing`, хотя новый вызов ввёл регрессию.

**Изменение:** `blame` использовать как evidence о возрасте строки. Статус `pre-existing` присваивать после проверки воспроизводимости дефекта на базе либо обоснованного рассмотрения. Хранить `introduced_by_change: true/false/unknown`, ссылку на base и причину. `unknown` не должен тихо снимать блокировку важного замечания.

### R10 · P1 · Eval overlay может писать вне временного worktree

**Где:** `bin/land-it:667`, особенно копирование guidance на строках 677–680.

Текущие `CLAUDE.md`, `REVIEW.md` и конфиг копируются поверх файлов исторического checkout через `shutil.copy2`. Если назначение в старом коммите — symlink, запись следует по нему. Временный worktree не изолирует файловую систему хоста.

**Подтверждено:** тестовый исторический `REVIEW.md`-symlink на sentinel в другой временной папке привёл к перезаписи sentinel текущим guidance, eval завершился с exit 0. Посторонние реальные файлы не затрагивались.

**Изменение:** безопасно создавать overlay, проверять каждый компонент пути, отклонять symlink в целевых путях и выход за root. Для недоверенной истории выполнять eval в отдельной среде с минимальным доступом. Аналогично проверить `.claude` как symlink-каталог и cleanup при частично неудачном worktree setup.

### R11 · P1 · CI-шаблон не обеспечивает новое ревью каждого нового SHA

**Где:** `templates/workflows/land-it.yml:29`, `templates/workflows/land-it.yml:44`.

Workflow запускается на `synchronize`, однако вызванный upstream code-review command предписывает остановиться, если Claude уже оставил комментарий в PR, а security action по умолчанию использует механизм пропуска повторного анализа PR без `run-every-commit: true`. Поэтому запуск job и новое ревью текущего commit — разные события. Это вывод по актуальным upstream-исходникам, а не результат запуска production workflow. См. [официальный code-review command](https://github.com/anthropics/claude-code/blob/main/plugins/code-review/commands/code-review.md) и [security action](https://github.com/anthropics/claude-code-security-review/blob/main/action.yml).

**Изменение:** привязать успешный review status к конкретному SHA; явно обеспечить повторный анализ после push, хранить предыдущую базу для инкрементального ревью. Не использовать наличие любого старого комментария как признак завершения проверки нового кода. Одного `run-every-commit: true` недостаточно для всей цепочки: в upstream publisher также есть пропуск публикации при наличии предыдущих security comments; нужна дедупликация отдельных дефектов и актуальный статус анализа. [Скрипт публикации security findings](https://github.com/anthropics/claude-code-security-review/blob/main/scripts/comment-pr-findings.js).

### R12 · P1 · Успех action не равен успешному анализу без замечаний

**Где:** `templates/workflows/land-it.yml`, `skills/init/branch-protection.md:23`.

В текущем upstream security action некоторые ошибки/пустые результаты обрабатываются как warning с нулевым количеством findings. Шаблон не проверяет отдельный контракт завершённого анализа. Required check может стать зелёным, хотя полезный анализ не состоялся. Источник: [реализация security action](https://github.com/anthropics/claude-code-security-review/blob/main/action.yml).

**Изменение:** отдельный итоговый policy job проверяет `completed`, `reviewed_sha`, валидный report, обязательные этапы, решение по важным findings. `error`, `skipped` и `clean` — разные состояния. Ошибка провайдера не должна означать «дефектов нет».

### R13 · P1 · Локальный trust имеет более узкую границу, чем обещает документация

**Где:** `bin/land-it:65`, `bin/land-it:88`, `bin/land-it:856`, `bin/land-it:989`.

Прямой `land-it trust` защищён от неинтерактивного запуска, но `hook expand` — публичная CLI-точка, которая доверяет переданным JSON-полям. Агент с произвольным shell/file access в рамках того же пользователя может вызвать её либо изменить локальные state/trust файлы. Это не отменяет полезности защиты от случайной правки конфига, но исключает обещание абсолютной защиты от такого агента.

**Изменение:** описать точную модель угроз. Использовать подтверждение runtime для согласования hooks, а отдельное согласование команд привязывать к показанному digest и авторизованному действию пользователя. Проверки и audit trail, которым нужно доверять в команде, вынести за права процесса автора изменений. Хранилище доверия записывать с блокировкой, уникальным temp-файлом и проверкой формата; учитывать конкурирующие сессии.

Доверие строке `npm test` не означает неизменность кода, который она запускает. Исполнение проверок из недоверенного PR требует изоляции независимо от hash команды.

### R14 · P1 · `{file}` внутри пользовательских кавычек допускает выполнение shell-подстановки

**Где:** `bin/land-it:893`.

`shlex.quote(path)` безопасен как самостоятельный shell argument, но не при подстановке внутрь уже существующих двойных кавычек. Пользователь естественным образом может записать `"{file}"` в formatter command. Тогда специальные символы имени файла снова могут интерпретироваться shell.

**Подтверждено:** в отдельном временном репозитории команда `printf "%s\n" "{file}"` и специально названный файл привели к созданию безвредного marker-файла через command substitution. Это касается такого пользовательского конфига; поставляемый шаблон использует `{file}` без внешних кавычек и сам этот вариант ошибки не содержит.

**Изменение:** поддержать структурированный `argv` с `shell=False` для per-file commands. Shell-режим сделать явно отдельным. До перехода валидировать способ использования placeholder и добавить тесты имён с метасимволами. Одной рекомендации «заключить путь в кавычки» здесь недостаточно.

### R15 · P1 · Сбой самого policy hook может пропустить операцию

**Где:** `hooks/hooks.json:37`.

У policy hook не задано поведение `onFailure: "block"`. Текущая документация Claude Code описывает продолжение операции по умолчанию при ошибке запуска, timeout и обычной ошибке hook; версия, заявленная в проекте, уже поддерживает настройку блокировки. Это проверено по документации, а не искусственным сбоем реальной пользовательской сессии. [Поведение hook при ошибке](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails).

**Изменение:** задать блокирующее поведение для тех hooks, которые являются policy gate, и проверить crash, отсутствующий executable и timeout в тестовой среде. Для информационных hooks режим может быть другим. Ошибка защитной проверки не должна молча выглядеть как разрешение.

### R16 · P1 · Статическое ревью подменяет проверку поведения в fallback

**Где:** `skills/preflight/SKILL.md:53`.

Общий fallback на subagent с diff и `REVIEW.md` применяется и к `/verify`. Чтение diff может найти дефект, но не подтверждает, что приложение запускается и пользовательский сценарий работает. Документация Claude описывает verify как запуск и проверку приложения. [Run and verify](https://code.claude.com/docs/en/skills#run-and-verify-your-app).

**Изменение:** отдельно определять fallback для code review, security и behavior checks. Для последнего нужны исполняемый сценарий, результат теста/запуска и, где уместно, скриншот. Если исполнение невозможно, статус `not_run` с причиной; policy решает, допустим ли такой результат.

## 5. Eval: достоверность, безопасность и полезность результатов

### E01 · P1 · Ошибка reviewer не даёт ненулевой код завершения eval

**Где:** `bin/land-it:667`, `bin/land-it:720`.

Ошибки кейсов попадают в отчёт, но команда может закончиться exit 0. Подтверждено подставным reviewer с ненулевым exit. Скрипт CI, который ориентируется на код завершения, сочтёт прогон успешным.

**Рекомендация:** задать контракт exit codes: успешный прогон; регрессия по явно включённому gate; ошибка инфраструктуры/формата; невалидный набор кейсов. По умолчанию инфраструктурная ошибка всегда должна быть машинно различима. Отчёт сохранять даже при ошибке.

### E02 · P2 · Judge принимает некорректный результат

**Где:** `bin/land-it:628`.

Не проверяется `returncode` judge, допускаются отрицательные `caught/findings`, парсится последний похожий JSON-фрагмент. Подтверждены принятие stdout при exit 3 и отрицательные счётчики.

**Рекомендация:** валидировать полный структурированный ответ, диапазоны и типы; требовать exit 0; не разрешать отрицательные показатели или `caught > expected`. Разделить результат judge и ошибку его исполнения. Добавить защиту от инструкций внутри текста review: этот текст — данные для оценивания.

### E03 · P2 · Сравниваются одинаковые ID, а не одинаковые наборы данных

**Где:** `bin/land-it:648`, `bin/land-it:702`.

Сравнение baseline учитывает список ID, но кейс под тем же ID можно дополнить другим дефектом, изменить диапазон/метку или изменить scoring implementation. Такие прогоны методологически несопоставимы. Для `--judge-cmd` имя scorer остаётся `judge:cmd` независимо от реальной команды.

**Рекомендация:** fingerprint содержимого всего корпуса, версии scorer и judge prompt/model/config. Явно хранить baseline и candidate; изменение корпуса требует новой базы сравнения. Модель reviewer, его инструкции и effort при этом могут различаться намеренно: именно их улучшение измеряет эксперимент.

### E04 · P2 · Исходное ревью теряется

**Где:** `bin/land-it:681`, `bin/land-it:690`, `skills/eval/SKILL.md:56`.

Skill предлагает читать вывод пропущенного кейса через `--only`, но CLI показывает лишь числа и не сохраняет текст reviewer. Трудно понять, был ли дефект пропущен моделью, неверно распарсен или неверно оценён judge.

**Рекомендация:** локальные artifacts на каждый run: запрос, raw response, нормализованные findings, judge output, stderr, timings, tool/model versions. `--only` тоже должен выдавать путь к artifact. Историю агрегатов можно коммитить, большие raw logs — отдельно с политикой хранения и удалением секретов.

### E05 · P2 · Citation scorer недостаточно надёжен для автоматического решения keep/revert

**Где:** `bin/land-it:546`, `bin/land-it:599`, `bin/land-it:604`.

Ссылка `file:line` рядом с дефектом может быть просто описанием контекста, а не найденной ошибкой. Один citation может засчитать несколько соседних bugs; сравнение по суффиксу пути может спутать одноимённые файлы. Пути с пробелами, emoji и некоторыми специальными символами, файлы без расширения и ссылки без `file:line` могут не распознаться. Ограничение частично честно описано в README.

**Рекомендация:** структурированные findings с `file`, `line_start`, `line_end`, `summary`, `evidence`, `severity`; matching по дефекту и уникальным сопоставлениям. Citation scorer оставить как явно грубый режим. Не объявлять LLM judge более точным без измерения согласия с человеческой разметкой.

### E06 · P2 · Корпус и статистическая процедура пока не доказывают улучшение reviewer

В репозитории отсутствует собственный committed corpus `.land-it/evals/`. Есть тесты механики, но нет набора реальных подтверждённых дефектов самого land-it. Verdict сравнивает один прогон с предыдущим, без оценки разброса, и трактует отсутствие измерения как ноль в отдельных сравнениях.

**Рекомендация:** начать с багов из этого аудита, добавить проверенные clean cases, разделить tuning и holdout. Для платных экспериментов заранее ограничивать число прогонов и бюджет. На значимых изменениях повторять несколько раз, показывать размер выборки и разброс. При отсутствии clean cases CLI уже выводит `noise: null`; нужно сохранить значение «неизвестно» также внутри `verdict`, где сейчас используется `noise or 0`. Начальное решение keep/revert — рекомендация, пока качество scorer не подтверждено.

### E07 · P2 · Идентификатор eval может выйти за каталог

**Где:** `bin/land-it:569`.

`--id` используется как часть пути без ограничения. Подтверждено: `--id ../escape` создаёт JSON за пределами `.land-it/evals/`. Для CLI, вызываемого агентом или будущим MCP, это нежелательный контракт записи.

**Рекомендация:** ограничить ID безопасным алфавитом, запретить разделители и traversal; проверять containment реального пути. Валидировать range, позитивные номера строк, порядок диапазона, kind и уникальность ожидаемых дефектов. Ошибки JSON показывать как понятную диагностику, не traceback.

## 7. Findings, ответы на PR и ночной sweep

### 7.1. Журнал замечаний

Сейчас дедупликация использует `(file, lower(summary))`. Это слишком грубо для одинаковых дефектов в разных местах и слишком строго для одного дефекта, описанного разными словами. Повторный thread может быть отброшен без сохранения связи с существующим finding.

Предлагаемый finding хранит стабильный ID, источник, severity, код/класс дефекта, нормализованный путь, location, evidence, проверенную версию кода, список связанных thread IDs, статус, причину решения и историю переходов. `fixed` должен ссылаться на исправляющий commit и проверку; `wontfix` и `pre-existing` — на evidence. При существенном изменении места уже отклонённую находку иногда необходимо открыть заново.

`round --reset` сейчас очищает ledger. Лучше разделить новый цикл ревью и архивирование findings: преодоление лимита раундов не должно уничтожать историю нерешённых проблем.

### 7.2. Ответы на PR

**Где:** `bin/land-it:750`, `bin/land-it:771`, `skills/respond/SKILL.md`.

- Загружаются review threads, но не все формы замечаний: обычные PR comments и summary reviews также могут содержать actionable findings. Заявление «каждое замечание» требует соответствующего покрытия либо более точного описания.
- В thread читаются первые 20 comments, наружу возвращается первый с обрезкой 1 500 символов и числом replies. Последние уточнения человека могут быть потеряны. Нужно пагинировать и возвращать релевантный контекст с признаком усечения.
- Outdated thread может иметь пустой `line`. Следует хранить исходную позицию/commit и корректно сопоставлять её с актуальным кодом.
- Ответ и resolve — две внешние операции. Если первая прошла, а вторая упала, повтор не должен дублировать ответ. Нужны idempotency key, журнал частичного успеха и отдельное возобновление resolve.
- Проверять принадлежность thread нужному repository/PR и текущие полномочия, особенно в MCP.
- Не писать «tracked in #issue», пока issue действительно не существует. При незаведённой задаче честно указывать отсутствие tracking.
- Сформировать один reviewable план ответов. Если пользователь уже явно поручил обработку с публикацией, не требовать дополнительного одинакового согласия для каждого thread по собственной инициативе; учитывать действующие ограничения runtime.
- Оставлять человеку его спорный thread на закрытие — полезное правило, которое стоит сохранить.

### 7.3. Ночной sweep

**Где:** `bin/land-it:804`, `skills/sweep/SKILL.md`, `templates/workflows/land-it-sweep.yml`.

`static_prefix` не даёт цели для glob без фиксированного начала, например `*.sql` или `**/auth/**`. Подтверждён пропуск таких high-risk patterns. Если есть другие подходящие кандидаты, они обходятся, а часть high-risk областей остаётся вне ротации. При только корневых исходниках fallback может не найти вообще ничего.

Рекомендуется строить цели из реально совпавших tracked files, хранить `last_scanned_sha/at` и выбирать давно не проверенные области. Календарный modulo не учитывает пропущенные ночи и успешность прошлого анализа.

Для scheduled workflow нужны budget/time limit, отмена устаревшего запуска, явная политика доступа к секретам, детерминированная дедупликация по fingerprint. Текущий поиск только 100 открытых issues не покрывает историю исправленных/отклонённых findings и позволяет повторять шум. Новые issues лучше публиковать отдельным шагом после проверки структуры результата.

Убедиться контрактным тестом, что используемый reviewer действительно принимает path target и умеет анализировать существующий код, а не только diff. Наличие skill с похожим именем этого не гарантирует.

## 8. Метрики и circuit breaker

**Где:** `bin/land-it:235`, `bin/land-it:447`, `bin/land-it:456`, `bin/land-it:472`, `bin/land-it:497`.

| Наблюдение | Рекомендация |
|---|---|
| Медиана считается выбором элемента `int(q*n)`; для `[2, 10]` получается 10 | Использовать обычную медиану 6 для чётной выборки; отдельно документировать метод p95 |
| Локальные runs дедуплицируются по имени ветки | Использовать change/PR ID, иначе повторно используемая ветка склеивает разные изменения |
| В статистику попадают в основном успешные stamps | Записывать старты, отказы, отмены и ошибки; иначе возникает смещение в пользу успешно завершённых случаев |
| Stamp без раундов учитывается как one-round pass | Различать `review_not_run` и проход с первого раунда |
| `hit_round_cap_pct` проверяет `> cap`, название допускает другое чтение | Развести reached/exceeded; учитывать остановленные preflight, которые не дошли до stamp |
| В GitHub human comments не учитываются inline review comments | Добавить их; пагинировать вложенные reviews/comments, сейчас лимиты по 100 |
| `hours_to_merge` — время от создания PR до merge | Называть cycle time; не выдавать его за реальные часы работы ревьюера |
| User/бот определяется по typename/login | Service user также может выглядеть человеком; нужен явный список automation identities |
| Reverts ищутся по сообщениям commits/названию PR | Называть это proxy; ручные откаты, roll-forward, incident fixes и feature-flag rollback не охватываются |
| First-parent commit не всегда соответствует одному PR | Учитывать стратегию merge и явно описать знаменатель |
| Revert rate округляется до сравнения с порогом | Порог применять к точному значению, округлять только отображение |
| Circuit breaker читает локальную base ref | Показывать актуальность ref; для серверного решения брать свежие подтверждённые данные |

Circuit breaker полезен, но его стоит вводить в команды сначала как наблюдение или рекомендацию с явной политикой включения. Нужны гистерезис, минимальная выборка, окно восстановления и объяснение, почему tier повышен. Рост количества approvals сам по себе не доказывает, что устранена причина инцидентов.

Основной измеряемый результат продукта: время ожидания и число циклов ревью снижаются, а частота подтверждённых дефектов после merge не растёт. Для этого нужны хотя бы связка PR → проверки → findings → инциденты, baseline до внедрения и достаточно наблюдений. Не делать причинных выводов по десяти stamps или одному изменению процента откатов.

## 9. GitHub workflow, branch protection и выпуск самого проекта

### 9.1. Контракт CI

Разделить jobs на детерминированные проверки, запуск reviewer и итоговую проверку policy. Для каждого результата хранить фактический `head_sha`, время, status и artifact. Успешное выполнение внешнего action не должно само по себе открывать merge.

Зафиксировать используемые actions и reviewer assets на проверенных commit SHA; особенно убрать зависимость security workflow от плавающего `@main`. Обновления проводить отдельными PR с проверкой контрактов. Для jobs добавить `timeout-minutes`, `concurrency` с отменой устаревших запусков, понятные error summaries и лимит расходов.

Форк-PR и PR от Dependabot требуют отдельного сценария с учётом ограничений секретов и token permissions. Нельзя решать это простым переключением на привилегированный trigger с исполнением кода из PR. Анализ исходников, запуск тестов и публикацию результата следует разделять по полномочиям. [GitHub: pull_request и fork PR](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request).

Проверить установку GitHub App, разрешения на inline comments/issues, фактическое имя required check, draft→ready, force-push, retarget, пустой diff, недоступную модель, rate limit и таймаут. Успешный validator JSON/YAML таких сценариев не подтверждает.

### 9.2. Политика одобрений

Текущий branch protection template задаёт статическое число approvals; таблица risk tiers в skill — динамическая. Это разные механизмы. CODEOWNERS и фиксированный approval count полезны, но сами не реализуют весь заявленный выбор по уровню риска.

Ввести описанную policy: какие tiers требуют человека, сколько независимых reviewers, кто может подтверждать, что считается свежим approval, кто и как делает исключение. Если нужна точная схема из исходной статьи, учитывать trusted authors и два человека для high-tier; нынешний land-it — адаптация части практик. Исходный материал также обсуждает merge queue, постепенный rollout и rollback, которые здесь не реализованы. [Статья Anthropic о code review](https://claude.dev/blog/solving-code-review-at-anthropic/).

`init --protect` должен сначала читать существующие правила, показывать diff и сохранять совместимые ограничения. Полная замена protection через PUT шаблоном может убрать прежние требования: в частности, `restrictions: null` отключает ограничения push, а переданный список required checks заменяет прежний. Нужен сценарий применения и отката только конкретного изменения. [GitHub REST: update branch protection](https://docs.github.com/en/rest/branches/branch-protection#update-branch-protection).

Для solo-профиля честно описать ограничения: self-approval не создаёт независимого review, а `enforce_admins: false` оставляет административный обход. Это допустимое решение пользователя, но не эквивалент строгому team policy.

### 9.3. Собственная инфраструктура land-it

В проекте есть `.claude/land-it.json`, но нет полного набора его же практик: собственного CI workflow, repo-specific `REVIEW.md`, собственного eval corpus и оформленного процесса выпуска. Это не дефект запуска CLI, а недостающая проверка продукта на себе.

Добавить минимальный CI: unittest, проверка манифестов и схем, smoke CLI, безопасность путей, тест упаковки. Выбрать и зафиксировать поддерживаемые версии Python/OS; Windows пометить unsupported до реализации locking и shell semantics. Для разработки дать contributor instructions, не путая их с инструкциями, загружаемыми в потребительском репозитории.

Релиз должен включать changelog с датой, tag, согласованные версии пакетов, manifest validation и тест установки в пустом репозитории. Проверять marketplace и plugin manifest отдельно. Опубликовать `CONTRIBUTING`, канал сообщения об уязвимостях, минимальную compatibility matrix и порядок миграции состояния.

## 10. Улучшения документации и пользовательского сценария

1. **Показать границы гарантий прямо в README.** Таблица: проверяется ядром / зависит от skill / обеспечивается CI / пока отсутствует. Убрать абсолютные формулировки про невозможность пропустить ревью.
2. **Развести режимы.** Local helper, team-enforced CI, nightly sweep, eval lab. Пользователь должен понимать, что именно установлено у него.
3. **Быстрый старт доводить до доказуемого результата.** Установка → проверка capabilities → настройка → согласование конкретных команд → smoke test → первый preflight. Не ограничиваться созданием файлов.
4. **Идемпотентный init.** Генерировать план и точный diff, сохранять пользовательские изменения, не создавать повторные imports и workflow, уметь обновлять схему.
5. **Понятный status.** «Что блокирует PR», «какой шаг следующий», «на каком SHA checks/review», «почему пропущен check», «есть ли незавершённый run».
6. **Повторные разрешения не должны становиться ритуалом.** Учитывать уже выраженную авторизацию. Для публикации давать конкретный draft/план; отдельное вмешательство человека нужно там, где оно реально меняет риск или полномочия.
7. **Общая краткая терминология.** Risk tier, severity, pre-existing, required check, review receipt и merge approval описать независимо друг от друга.
8. **Отдельные примеры стеков.** Python, Node, Go и monorepo; давать существующие команды проекта, не навязывать npm-шаблон всем.
9. **Версионировать замеры стоимости.** Дата, provider/model/version, effort, размер diff, метод подсчёта и artifact. Один эксперимент с `max` не является прогнозом стоимости для любого проекта.
10. **Синхронизация языков.** EN/RU держать в одной структуре, проверять совпадение ключей конфига, таблиц CLI и ограничений при релизе.
11. **Не исключать dependency security безусловно.** Шаблон `REVIEW.md` предлагает пропускать lockfiles. Для стиля это разумно, но изменения зависимостей и supply-chain policy всё равно должны проверяться отдельным этапом.
12. **Указать проверенные возможности платформы.** `bin/` на PATH — поддерживаемая возможность текущих Claude Code plugins; для другой среды её нужно проверять. В fallback использовать кавычки и package-relative paths. [Claude Code plugin layout](https://code.claude.com/docs/en/plugins-reference#standard-layout).

## 11. Версия для ChatGPT и Codex: что доступно сейчас

Этот раздел опирается на официальные страницы, прочитанные 24.10.2026. Возможности конкретного аккаунта и среды нужно проверять при реализации; установка пакета не гарантирует наличие локального Git, runner или GitHub credentials.

### 11.1. Платформенные факты

- OpenAI описывает plugins как пакет skills, MCP и при необходимости UI; общий каталог обслуживает ChatGPT и Codex. UI необязателен. [Plugin architecture](https://developers.openai.com/plugins/concepts/plugins).
- Существует официальный путь переноса Claude plugin. Skills и helpers можно адаптировать; Claude-specific инструкции и настройки требуют пересмотра. Marketplace approvals автоматически не переносятся. [Перенос Claude Code plugin](https://developers.openai.com/plugins/guides/submit-claude-plugin).
- Lifecycle hooks поддерживаются для вручную установленных Codex desktop plugins; пакеты с такими hooks сейчас не допускаются в публичный каталог. Для нового portable manifest документация предлагает корневой `plugin.json` и `extensions.com.openai`; `.codex-plugin/plugin.json` остаётся совместимым вариантом. Установка через web сама по себе не разворачивает hook scripts в среде исполнения. [Packaging и bundled hooks](https://developers.openai.com/plugins/build/plugins).
- В Codex документированы `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop` и другие события с trust review. Для `apply_patch` payload содержит command, а не обязательный `file_path`; `turn_id` — полезное расширение. `UserPromptExpansion`, на котором построен текущий trust, в опубликованном списке нет. Hooks рассматриваются как ограниченный guardrail. [Hooks](https://learn.chatgpt.com/docs/hooks).
- Инструкции репозитория для Codex размещаются в `AGENTS.md`; есть отдельная рекомендация для Code Review Rules. Не следует предполагать автоматическую интерпретацию Claude-импорта `@REVIEW.md`. [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
- `codex exec` подходит для scripts/CI, поддерживает JSONL events, запись финального ответа и `--output-schema`. Это возможный reviewer adapter с контролируемым форматом. [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).
- MCP plugin можно подключить и проверить в ChatGPT Work; для первого прототипа custom UI не требуется. [OpenAI plugin quickstart](https://developers.openai.com/plugins/quickstart).

Это исключает две ошибочные крайности: считать, что в Codex вообще нет hooks, или обещать, что текущий Claude hooks-файл заработает без изменений во всех вариантах ChatGPT.

### 11.2. Варианты продукта

| Вариант | Для кого | Что может делать | Что требуется | Рекомендация |
|---|---|---|---|---|
| Локальный Codex plugin | Разработчик с checkout | Preflight, checks, findings, eval, локальные hooks | Runtime с нужными capabilities, Python/Git, отдельный адаптер | Первый этап переноса |
| ChatGPT plugin через MCP | Автор PR, тимлид, reviewer | Статус PR, риск, результаты CI, ответы, запуск контролируемого review | MCP service, auth, runner или CI | Следующий этап |
| Пакет skills без hooks | Пользователь каталога | Повторяемые инструкции и оркестрация доступных tools | Доступные инструменты среды | Ограниченный режим с честным описанием гарантий |
| Анализ переданного diff в обычном чате | Разовый пользователь | Объяснение и рекомендации по коду | Достаточный контекст | Демонстрационный режим; без автоматического допуска к merge |

### 11.3. Рекомендуемая архитектура

Один продукт и одно ядро policy/state. Платформенные пакеты различаются интеграцией, а не копиями бизнес-логики.

```text
Claude Code skills + hooks ───┐
                             │
Codex skills + hooks ─────────┼── land-it core ── Git / checks runner
                             │       │
ChatGPT skills ── MCP API ────┘       ├── reviewer adapters
                                     ├── findings / receipts / evals
                                     └── GitHub policy + публикация
```

Предлагаемая структура, не текущие файлы:

```text
bin/land-it                       # тонкая CLI-точка входа
land_it/
  config.py                      # схема, миграции, policy resolution
  git_context.py                 # repo, refs, diff, snapshots
  runner.py                      # процессы, timeout, logs, cancellation
  state.py                       # runs, receipts, locks, versions
  policy.py                      # risk и required stages
  findings.py
  evals.py
  metrics.py
  providers/claude.py
  providers/codex.py
  integrations/github.py
adapters/claude/                  # hook input/output mapping
adapters/codex/
skills/                          # общие workflow или исходники генерации
packages/                        # сборка платформенных дистрибутивов
schemas/
tests/
```

MCP слой подключать к библиотечным функциям, а не к shell-командам с параметрами пользователя. При первом рефакторинге достаточно нескольких модулей; не создавать сложный framework заранее.

### 11.4. Provider-neutral конфигурация

Канонический путь предлагается `.land-it/config.json`. Старый `.claude/land-it.json` читать для совместимости; при наличии обоих не выбирать молча — валидировать согласованность и предлагать явную миграцию.

Общие настройки: checks, risk, required stages, limits, base selection, policy version. Provider-настройки: adapter, model, effort mapping, availability, auth mode. Модели и API keys не должны быть зашиты в skills или переноситься в Git. Секреты хранятся вне project config.

Модель независима от платформы исполнения. «Codex adapter доступен» не означает, что любой model name или effort поддерживается. `max` и `ultra` из Claude workflow нельзя механически передавать в другой CLI. Capability check должен выявлять доступность и нормализовать effort в рамках общего контракта.

### 11.5. Что менять в skills и hooks

| Сейчас | Предлагаемое изменение |
|---|---|
| `/land-it:preflight`, Claude Skill tool | Общий workflow с платформенным способом invocation |
| `/simplify`, `/code-review`, `/security-review`, `/verify` | Явные reviewer capabilities и fallback, выбранные адаптером |
| `.claude/land-it.json` | Общий конфиг с backward compatibility |
| `CLAUDE.md` + `@REVIEW.md` | Общие review rules и короткие platform instructions; для Codex — `AGENTS.md` |
| `UserPromptExpansion` выдаёт trust | Отдельное проектирование подтверждения на поддерживаемом runtime; не эмуляция пользовательского действия JSON-полями |
| `PostToolUse.file_path` | Нормализация event payload; `apply_patch` может изменять много файлов |
| Ledger только на branch | Change/PR ID и отдельный session/turn/run ID |
| Чтение текстового вывода reviewer | Единая schema findings + raw artifact |

Для hook adapter нужны fixture-тесты реальных payload каждого runtime. Особенно проверить повторный Stop после continuation, subagents, несколько tool calls одновременно, shell edits, multi-file patch, отмену и timeout. Совпадение имён событий не доказывает одинаковую семантику.

### 11.6. Минимальный контракт MCP для ChatGPT

Это проект API, а не утверждение о существующих tools:

| Tool | Назначение и ограничение |
|---|---|
| `get_capabilities` | Версии, поддерживаемые операции и доступные runner/provider |
| `get_repository_status` | Известные repo/PR/head/base и причины блокировки |
| `assess_change` | Diff/risk по проверяемому SHA; неизвестная база — ошибка |
| `start_preflight` | Асинхронный запуск с allowlisted profile и лимитами |
| `get_run` | Статусы этапов, evidence и ссылки на логи |
| `list_findings` | Полный список с пагинацией, фильтрами и версиями |
| `propose_resolution` | Подготовка решения с evidence, без автоматического объявления «fixed» |
| `prepare_pr_response` | Конкретный draft ответов и план изменений |
| `publish_pr_response` | Проверенная запись по plan ID, expected head и idempotency key |
| `get_metrics` | Метрики с определениями, окнами и качеством данных |

Первый MCP MVP может ограничиться чтением статуса, findings и подготовкой ответов. Merge и произвольный shell не нужны для проверки полезности ChatGPT-версии.

Для записи требуются repository-level authorization, привязка пользователя/организации, проверка свежести плана и защита от повторов. Входные PR descriptions, comments и код считать данными, а не инструкциями, меняющими полномочия. Нельзя разрешать tool `run_command(any_string)` под видом проверок: запускать зарегистрированные check profiles в изолированном runner.

Долгое ревью — `run_id` со статусами и отменой. Не держать один MCP вызов до окончания всех тестов. UI можно добавить позднее для списка findings и карты блокеров; сначала достаточно структурированных tool results и ясного текстового ответа.

## 12. Доказательства выполнения: основной контракт следующей версии

Следующая версия должна отвечать не только «зелёный ли tree», но и «что именно, кем, когда и при какой policy проверено».

Предлагаемый состав receipt:

```json
{
  "schema_version": 1,
  "run_id": "opaque-run-id",
  "change_id": "opaque-change-id",
  "repository_id": "canonical-repository-id",
  "head_sha": "commit-sha-or-null-for-local-snapshot",
  "tree_sha": "git-tree-sha",
  "base_sha": "review-base-sha",
  "policy_digest": "digest",
  "guidance_digest": "digest",
  "checks": [{"id": "unit", "status": "passed", "artifact_id": "log-id"}],
  "reviews": [{"kind": "code", "status": "completed", "artifact_id": "report-id"}],
  "risk": {"floor": "medium", "effective": "high", "reasons": ["public API change"]},
  "finding_set_digest": "digest",
  "decision": "eligible-for-pr"
}
```

Это эскиз, не готовая JSON Schema. Дополнительно нужны timestamps, duration, provider/model versions, check command/environment fingerprint, skipped-stage reasons, required human approvals и состояние freshness. Для server-issued receipt требуется проверяемый issuer; подпись локальным ключом, доступным тому же агенту, не создаст независимой гарантии.

Правила жизненного цикла:

1. Изменение кода или контекста делает зависимые результаты устаревшими.
2. `started` никогда не означает `completed`.
3. Ошибка, отсутствие данных и чистый результат различаются машинно.
4. Состояние `fixed` сопровождается evidence и связано с проверенным commit.
5. Полный gate рассчитывается из receipts и policy, а не из текста PR body.
6. Локальная готовность к созданию PR и разрешение merge — отдельные решения.

## 13. План реализации по этапам

Это предлагаемый порядок работ. Оценки сроков нужно уточнить после выбора поддерживаемых сред и уровня обязательности server gate; сейчас корректнее согласовать критерии завершения, чем обещать точные дни.

| Этап | Содержание | Когда считать готовым |
|---|---|---|
| **A. Исправление гарантий 0.6.x** | R01–R10, R14, ошибки eval/judge, строгие exit codes; честные границы README | Воспроизведённые дефекты закрыты regression-тестами, старые тесты проходят |
| **B. Надёжный CI и процесс PR** | R11–R13, R15–R16, fresh-SHA review, итоговый policy job, безопасные workflow, разрешения | Новый push требует актуального результата; ошибка reviewer не становится зелёной проверкой |
| **C. Общее ядро** | Модули, schema config/state/receipts/findings, JSON CLI, миграции | Claude-версия сохраняет поведение, contracts не зависят от provider |
| **D. Локальный OpenAI MVP** | Codex adapter, skills, AGENTS guidance, hooks/trust mapping, ручная установка | Полный smoke от чистого repo до preflight; проверены patch/shell/stop и отсутствие capabilities |
| **E. ChatGPT MCP MVP** | Статус PR, run/findings, drafts; затем контролируемая публикация | Реальная авторизация и изоляция, корректное поведение stale/partial/error; нет arbitrary shell |
| **F. Качество reviewer и эксплуатация** | Корпус, holdout, версии judge, metrics, budgets, sweep history | Понятно, по каким данным изменение reviewer лучше baseline и сколько оно стоит |

Локальный Codex MVP можно начать параллельно с изучением MCP-контрактов после стабилизации схемы. Публичный каталог и автоматический merge следует планировать после end-to-end проверки гарантий, а не использовать как критерий первого прототипа.

## 14. Обязательная матрица проверки следующей версии

| Группа | Сценарии |
|---|---|
| Check freshness | PASS→FAIL без edit; команды меняют файл; edit во время check; timeout/cancel; пустые checks |
| Review lifecycle | Прерывание после round; reviewer error; повтор того же tree; edit после review; cap/reset |
| Git context | Неизвестная база; shallow clone; новая target branch; rename high→low; deletion; Unicode/NUL parsing |
| Workspace | Worktree; submodule; detached/unborn HEAD; path с пробелом; symlink; sparse checkout; conflicts |
| State | Две сессии; несколько worktrees; collision имён веток; reuse branch; повреждённый JSON; migration; GC |
| Trust | Изменение команд; совпадение показанного digest; подставной hook payload; ограниченные filesystem permissions |
| Shell paths | `{file}` внутри и вне внешних кавычек; пробелы, apostrophe и `$()` в имени; структурированный argv |
| GitHub | Локальный HEAD ≠ remote head; push/rebase/retarget; fork; draft→ready; action error; pagination |
| Findings | Старая строка с новой регрессией; дубли в разных местах; новые thread IDs; outdated line; reopen |
| Writes | Reply успешен, resolve упал; повтор запроса; stale plan; другой repo/thread; revoked permission |
| Eval | Traversal ID; symlink overlay; changed corpus; invalid/negative judge JSON; reviewer exit; raw artifacts |
| Metrics | Чётная медиана; inline comments; service users; >100 reviews; повторное имя branch; aborted runs |
| Runtime adapters | Реальные Claude/Codex payload fixtures; apply_patch; shell edit; nested tools; Stop continuation |
| Installation | Чистая среда; отсутствуют Python/Git/provider; неподдержанный hook; нет auth; upgrade/uninstall |

Это не требование сразу написать сотни тестов. Сначала regression-тесты подтверждённых дефектов и несколько end-to-end контрактов, затем расширение по реально заявленной поддержке.

## 16. Рекомендуемое решение о следующем шаге

Выбрать **stabilization → общее ядро → локальный Codex adapter → ChatGPT MCP**. Первым рабочим пакетом сделать исправление freshness/rounds/risk/eval isolation с regression-тестами. Это повысит качество текущей Claude-версии и предотвратит перенос ошибок.

После стабилизации прототип OpenAI должен показать один полный сценарий: изменение → checks → независимое review → findings → проверяемый receipt → готовность к PR. Для ChatGPT следующим доказательством полезности станет сценарий «покажи, что блокирует этот PR, подготовь ответы и запусти недостающую проверку» через MCP.

**Результат, к которому стоит стремиться:** land-it одинаково объясняет и подтверждает готовность изменения независимо от того, помогал с кодом Claude, Codex или ChatGPT; доверие к merge определяется проверяемыми результатами и политикой репозитория.

## 17. Параллельные изменения, замеченные при завершении аудита

После изучения исходного чистого snapshot в рабочем дереве появились изменения `bin/land-it` и `tests/test_land_it.py`. Они сделаны вне данного аудита и оставлены без вмешательства. Поэтому результат «39 тестов, OK» относится к проверенному исходному состоянию и не является подтверждением всего нового diff.

При чтении нового diff обнаружены улучшения, уже частично реализующие рекомендации:

- Для outdated threads добавлен `originalLine` и fallback позиции.
- Добавлена отдельная команда `threads resolve`, диагностика частичного успеха reply/resolve и тест ошибки resolve. Это снижает риск повторной публикации; полноценная идемпотентность и проверка актуального thread state остаются отдельными задачами.
- Добавлены разбор PR number/`#N`/URL и обработка пустого reply payload. Для URL необходимо также проверять repository identity: извлечение только номера не устанавливает целевой repo.
- Расширена обработка sweep patterns через совпавшие файлы. Прежний пример `*.sql` с одним подходящим файлом уже учтён новым тестом. Полноту покрытия ещё нужно проверить: для matches с разными корневыми сегментами общий префикс может быть пуст, а корневые файлы требуют явного сценария.
- Усилена очередность решений hook: запреты рассматриваются раньше запроса подтверждения для составной команды. Это полезно, но не устраняет ограничения regex и локального trust boundary.
- Eval scan отличает повторное применение изменения через revert of revert от нового инцидента.

Эти пункты следует считать **изменёнными после базового аудита**, а не повторно ставить в очередь как совершенно отсутствующие. Перед реализацией рекомендаций нужно сопоставить их с последним diff и повторить только релевантные проверки. Остальные выводы отчёта привязаны к зафиксированному commit, что позволяет проверить их даже при продолжающейся параллельной разработке.
